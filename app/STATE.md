## 1. 目的と環境

- 既存Excel VBAの買掛帳（`KTABLE`、2020年以降の仕入・前払・決済・調整等）を、Windowsで利用するローカルアプリに置き換える。
- 利用者は1名。フロントエンドはHTML/JavaScript、バックエンドはNode.js、保存先はSQLite。Accessは使わない。
- 画面は左サイドバーで直接移動し、入力部分は必要に応じて折りたたむ。未保存の編集を残して画面移動する場合は警告する。
- 主な画面: ダッシュボード／仕入登録／INVOICE管理／決済・充当／送金一覧／仕入先マスター／設定・バックアップ。

## 2. データ・金額の基本原則

- 仕入元帳の円金額が正本。外貨から再計算して上書きしない。
- 仕入金額にはマイナス（返品・値引等）も存在する。マイナス行を自動的に銀行返金や送金として扱わない。
- INVOICEには内部IDと、ユーザーが扱うINVOICE番号を別に持つ。
- 発注番号は商品IDとして使われることがあり、一意の仕入取引IDではない。同じ発注番号が複数の仕入・INVOICEに現れる。
- 支払通貨コードは3文字。通貨は当面JPYとUSD。JPYは円単位、USDはセント単位の整数として保存し、浮動小数点誤差を避ける。
- INVOICEの「商品代金（外貨）」と「請求総額（外貨）」を分ける。差額には運賃などが含まれ、円の仕入元帳に必ずしも含まれない。
- 支払残高はINVOICE総額と有効な充当額から算出する。支払済フラグのみで残高を管理しない。

## 3. 仕入登録

- 元帳から次の4列をタブ区切りで貼り付ける: `仕入先コード`／`発注番号`／`仕入日`／`合計金額`。
- 「読み込む」でプレビューに展開し、貼り付け欄は自動で折りたたむ。ただし読み込み時点では原文を消さない。
- 複数の仕入行を選び、INVOICE番号・日付・通貨・商品代金・請求総額等を指定して関連付ける。1回の貼り付けから複数INVOICEを割り当てられる。
- INVOICE未着の仕入行も登録可能。
- 保存成功時のみ処理済み入力をクリアし、未処理行は残す。保存失敗時は入力を保持する。
- 既存INVOICEの割当を無言で上書きしない。同一割当はスキップ、異なる割当は確認し、決済済みのものは専用訂正フローで扱う。
- 重複チェックは仕入先コード・発注番号・仕入日・合計金額の4項目完全一致で行い、今回の読み込み内（注意・登録可能）と既存登録データ（要確認・明示的許可で登録可能）を区別する。発注番号のみの一致やプラス・マイナスの違いは重複扱いしない。
- 仕入明細に登録日時・登録バッチIDを保存する。仕入先コード＋発注番号ごとに枝番を自動採番し、変更・取消後も再採番や欠番再利用をしない。内部の仕入IDは別に保持する。返品・再納入は独立行として残す。

## 4. INVOICE管理

- 仕入先・番号・日付・状態・通貨等で検索する。
- INVOICEごとに仕入明細、元帳円合計、商品代金（外貨）、請求総額（外貨）、期日、決済・充当履歴、未決済残高を確認する。
- 仕入日とINVOICE日付は別項目。
- INVOICE画面で選択したINVOICEを内部IDで決済・充当画面に渡す。複数選択も想定し、元画面へ戻れるようにする。
- 決済済みINVOICEの編集は制限し、必要に応じて訂正フローを使う。

### INVOICE番号テンプレート（確定）

- 仕入先マスターにテンプレートを保存する。固定文字列はそのまま使用できる。
- 例: `INV-CE OXD14-BCHSA-10MHZ`、`ZKW-A-{yymm}MK01`。
- 日付変数: `{yyyy}`、`{yy}`、`{mm}`、`{dd}`、`{yymm}`、`{yymmdd}`、`{yyyymmdd}`。
- 変数の基準は**仕入日**。`{mm}` は独自の置換ルールで月を表し、分ではない。
- 生成結果は手動修正可能。テンプレートがない場合は自由入力。
- 複数の選択仕入行で仕入日が異なる場合は、最小の仕入日を自動採用する。
- 支払予定日の算出にはINVOICE日付を使用する。
- テンプレートに仕入先名を自動挿入する要件はない。例中の会社名は支払う側の自社名であり、仕入先名ではない。

## 5. 支払条件と予定日

- 標準: INVOICE月末締め、翌々月10日払い。10日が土曜日・日曜日なら翌月曜日へ繰り延べる。祝日・年末年始の自動判定は行わない。
- 海外の長期休暇等により予定日を個別変更できる。算出した基準期日と変更後の期日を区別し、変更理由を残す。
- 祝日・年末年始・海外休暇による変更は手動で予定日を修正し、理由を記録する。祝日データの管理機能は設けない。

## 6. 決済・充当

- 方法: 振込、前払充当、売掛相殺。
- 1回の決済を複数INVOICEへ充当でき、1枚のINVOICEを複数回に分けて決済できる。
- 同一決済でまとめる対象は支払先・受取人コード・通貨の整合を確認する。異なる通貨を単純合算しない。
- 決済総額と充当合計は一致させ、各INVOICEの未決済残高を超える充当を禁止する。超過額・ゼロ・負数・空欄・通貨小数桁数違反等を入力欄付近に表示し、確定を無効化する。
- 前払金は実際の送金日に支払記録を作り、仕入への前払充当日は仕入日とする。前払残高を超える充当を禁止する。
- 売掛相殺は売上INVOICE合計と実入金額の差額、および入金案内（例: `LESS CW INVOICES`）を確認してから、相殺日（売掛入金日）・相殺額・対象買掛INVOICE・備考を手入力する。複数INVOICEに充当できる。売上INVOICE自体の登録は不要。
- 決済履歴から日付・備考・充当先・充当額等を修正できる。金額変更時は充当合計の整合性を再検証する。決済方法変更は原則取消・再登録。
- 取消は物理削除せず、決済・充当を無効化して残高を再計算する。変更履歴を残す。
- 旧Excelの「支払済」等の状態から、根拠のない銀行送金履歴を自動生成しない。

## 7. 送金一覧

- 支払予定月で絞り込み、INVOICEを個別・一括・支払先単位で選択できる。
- 支払先・受取人コード・通貨別に集計し、INVOICE明細は開閉可能にする。仕入先コードが異なっても、これらが一致すれば同じ送金先に集計できる。
- 集計結果をExcelに貼り付けやすいタブ区切りでコピーできる。
- 仕入先と実際の支払先が異なる場合があるため、仕入先マスターの支払先を利用する。
- 受取人コード（みずほ銀行の支払先マスターID）は送金一覧で表示するが、**コピー対象に含める必要はない**。銀行との自動連携も行わない。
- 一覧作成・コピーだけでは決済済みにしない。実際の送金を確認した後、ユーザーが明示的に送金完了を確定する。
- 確定時に実際の送金日を一括指定し、決済履歴とINVOICEへの充当を整合的に登録する。複数件の一括確定・一部送金に対応する。
- 送金後の訂正・取消は決済履歴から行う。

## 10. SQLiteの論理テーブル案

> 以下は**設計案**。列名・キー・制約・移行方法は実装前に確定する。

| テーブル | 役割・主要項目 |
| --- | --- |
| `Suppliers` | 仕入先ID、コード、名称、支払先、通貨、受取人コード、国・原産国・船積地、取引内容、使用、決済区分、支払条件、番号テンプレート |
| `Purchases` | 仕入ID、仕入先ID、発注番号、仕入日、元帳円金額、INVOICE関連付け、登録日時 |
| `Invoices` | INVOICE内部ID、仕入先ID、表示番号、INVOICE日付、通貨、商品代金、請求総額、基準期日、実効期日、変更理由 |
| `Payments` | 決済ID、支払先・仕入先の参照、決済方法、通貨、総額、実行日、備考、取消状態 |
| `Allocations` | 充当ID、決済ID、INVOICE ID、充当金額、充当日、取消状態 |
| `AuditLog` | 操作種別、対象ID、変更前後の記録、日時、理由 |

詳細設計で具体化する論理構造:

- 前払金は仕入明細・発注番号なしでも登録できる。支払時に用途（仕入対象／仕入対象外／送料・諸費用／未確定）を指定でき、後から変更可能。仕入対象外は取消・調整ではなく正常な支払として完了し、他の仕入への充当に使用できない。残高・使途確定・取消を管理するための `Prepayments` 等の構造を設計する。
- 売掛相殺は売上INVOICEのDB登録なしで、買掛側の相殺記録と充当・備考を保持する（`Offsets` 等の詳細構造を設計する）。
- 仕入明細1件は最大1枚のINVOICEに所属するため、`Purchases.invoice_id`（NULL可）を基本案とする。1枚のINVOICEに複数仕入明細を関連付けられる。
- 支払先は独立マスターを作らず仕入先マスターの支払先・受取人コード・通貨で集計する。支払実績には送金時点の支払先情報のスナップショット保持を検討する。
- 金額整数化、CHECK制約、外部キー、トランザクション、取消履歴の詳細。

## 13. 追加確定事項（2026-11-20・業務フロー）

### 仕入重複・返品
- 4項目完全一致を重複候補とする。今回の読込内の一致は「注意」、既存データとの一致は「要確認」で、後者は明示的な承認を必要とする。いずれも正当な重複仕入の登録を禁止しない。
- 登録日時と登録バッチIDを自動記録する。仕入先コード＋発注番号ごとの枝番を1から自動付与し、取消後も再利用しない。元の発注番号は書き換えない。
- 返品（負数）と再納入（正数）はそれぞれ独立した仕入明細。自動相殺・自動送金記録作成はしない。

### 前払い・仕入対象外
- 前払いは発注番号・仕入明細の存在を前提としない。支払時点では仕入計上されるか未確定の場合がある。
- 支払時から「仕入対象」「仕入対象外（サンプル品・消耗品費等）」「送料・諸費用」「未確定」を選択可能とし、後から使途を確定・変更できる。
- 仕入対象外・送料等は支払取消ではなく、仕入明細を伴わない正常な支払記録として完了する。勘定科目の自動仕訳は行わず、必要ならメモを残す。
- INVOICEに商品代金と送料が含まれる場合、請求総額で決済を照合し、実際に別送金していない限り送料を別決済に分解しない。
- 前払残高は有効な使途確定・充当から計算し、残高を超えた充当を禁止する。

### 売掛相殺
- 売上INVOICE総額と実入金額の差額から候補を見つけ、入金案内等で確認してから買掛側へ登録する。差額だけで自動確定しない。
- 相殺日＝売掛金の入金日、相殺金額は手入力。複数買掛INVOICEへの充当を認め、備考に根拠を残せる。売上側のINVOICE管理機能は作らない。

### 送金・仕入先マスター
- 異なる仕入先コードでも同一支払先になり得る。送金一覧は支払先・受取人コード・通貨が一致するものを集計する。受取人コードはみずほ銀行の登録先IDであり、画面表示はするがコピーは不要。
- 実際の送金日を一括指定して、選択した複数INVOICEの送金を確定できる。部分送金可。送金一覧の表示・コピーは決済確定としない。
- 仕入先マスターの必須項目はコード・仕入先名。送金時には支払先・支払通貨を必須とする。

### 休日・履歴・起動
- 支払予定日の自動繰延は土日だけ。祝日・年末年始・海外休暇は必要に応じ手動変更し、理由を記録する。
- 登録・修正・取消の監査履歴を保存し、決済取消は論理取消とする。複数テーブルの更新はトランザクションで一括実行し、失敗時はロールバックする。DB構造更新前にバックアップする。
- Windowsのローカルブラウザ型アプリを採用する。Node.jsをショートカットから起動し、Edge等で画面を開く。業務データはブラウザ内ではなくSQLiteに保存する。

## 15. SQLite詳細設計の追加確定事項（2026-11-20）

- **仕入とINVOICE**: 仕入明細1件につき関連するINVOICEは最大1枚。INVOICE未割当を許可する。1枚のINVOICEには複数仕入明細を紐付けられる。`Purchases.invoice_id`（NULL可）を基本設計とする。
- **前払返金**: 現時点では業務実績がなく、返金登録の専用機能は初期実装に含めない。返金が発生した際は仕様を追加する。
- **前払の部分充当**: 1回の前払金を複数INVOICEに分けて充当可能とする。充当額合計は利用可能な前払残高を超えない。
- **支払先マスター**: 別マスターを作らず、既存の仕入先マスターの「支払先」「受取人コード」「支払通貨」を利用する。これらの組み合わせで送金先を集計する。
- **決済区分**: 既存マスターは「前払」「相殺」、通常送金は空欄。新アプリでは「通常送金」「前払」「相殺」を明示的な値として扱い、旧空欄は通常送金と解釈する。仕入先マスターの決済区分は既定値であり、実際の個別決済方法は決済記録で保持する。
- **仕入対象外のINVOICE**: サンプル品、消耗品、送料等、仕入明細が存在しない場合でも、INVOICE番号・日付・商品代金・請求総額・通貨等を登録・保存できる。

## 18. 実装前の最終確認事項（2026-11-20）

- **前払い時のINVOICE**: 前払い登録にはINVOICEの登録を必須とする。発注番号・仕入明細の登録は不要。仕入対象外INVOICEも許可する。

- **登録済み仕入明細の修正**: 仕入日・金額等を修正可能とし、変更日時・変更前後の値・理由等を監査履歴に記録する。INVOICE紐付け済みの場合は整合性を検証する。
- **INVOICE番号の重複**: 同じ仕入先の同じINVOICE番号を登録しようとした場合は警告する。明示的な確認を経た場合に限り重複登録を許可し、承認操作を履歴に残す。DB上の一意制約で禁止しない。

## 19. SQLite物理設計 v0.1.0（2026-11-20）

- 初期DDL案は別ファイル `schema.sql`。SQLiteで構文検証済み（10テーブル）。実装前のレビュー対象とする。
- 主要テーブル: `suppliers`, `import_batches`, `invoices`, `purchases`, `payments`, `allocations`, `advance_uses`, `invoice_adjustments`, `audit_log`, `schema_migrations`。
- `purchases.invoice_id` はNULL可。仕入明細は最大1枚のINVOICEに属する。INVOICEは仕入明細ゼロ件でも登録可能。
- 仕入の枝番は `(supplier_id, order_number, branch_number)` で一意。取消済みも含め最大枝番+1をトランザクション内で採番する。
- 仕入の4項目重複とINVOICE番号重複は**警告型**。DBで一意制約を設けず、確認操作を監査履歴に残す。
- 決済 `payments` は通常送金／前払送金／売掛相殺を区別し、`allocations` により複数INVOICEへの充当を表現する。支払先名と銀行受取人コードは決済時点のスナップショットを保持する。
- 前払はINVOICE登録を前提とし、送金時点で未充当残高を許可する。後日INVOICEへ部分充当可能。仕入対象外INVOICEへの充当も通常の充当として記録する。`advance_uses` は**INVOICEへ充当しない前払残余を費用処理する場合に限る**補助記録とし、同額を`allocations`と二重計上しない。
- INVOICE請求額との差額を理由付きで精算する場合のみ、`invoice_adjustments` を使う。理由メモだけでは残高を減らさない。調整額は符号付き整数。
- 金額は通貨の最小単位の整数。請求残高 = 請求総額 - 有効充当合計 - 有効調整合計。前払利用可能額 = 前払総額 - 有効充当合計 - 有効費用処理合計。
- DB制約は単一行の整合性と参照整合性を担当。複数テーブル間の残高上限・通貨一致・取消整合性はNode.js側で `BEGIN IMMEDIATE` による単一トランザクションで検証・更新する。`PRAGMA foreign_keys=ON` を接続ごとに有効化する。
- 送金先のグループ集計は仕入先マスターの支払先・受取人コード・通貨で行う。**複数仕入先を一括送金した場合でも、決済レコードは仕入先単位に分け、画面で送金グループとしてまとめる**初期設計とする。銀行の1送金と内部決済レコードの対応を厳密に管理する必要が生じた場合、`transfer_batches` 等の追加を検討する。
- DB上の `CHECK` による日付形式は字面の検査にとどまるため、存在しない日付・通貨小数桁・支払条件はアプリ側で厳密に検証する。
- `schema_migrations` で適用版を記録し、更新前にSQLiteバックアップAPIで退避する。

### 実装前に注意する点

- 前払登録時の「INVOICE必須」は、前払の初回登録にINVOICEの存在確認を課す業務ルール。前払を直ちに全額充当する意味ではない。
- 決済額と請求額の差額は、**未払残として維持**するか、**理由付き調整を明示登録**するかを操作で区別する。
- `schema.sql` はDDLの初版。前払使途変更・相殺取消・仕入先を跨ぐ一括送金のUI/API設計に合わせ、実装前に制約とトランザクションのテストを追加する。

- 月別転記用紙の仕入額は、決済の充当先INVOICEに紐付く有効な仕入明細の円合計。同じINVOICEへの充当が決済内に複数あっても一度だけ加算する。紐付けなしの場合は「—」。分割決済で同一INVOICEへの充当が別行にある場合は、その各行に仕入額を表示する。
- 月別転記用紙は、決済履歴、業務フロー、ダッシュボード、送金一覧の予定・実績から開ける。業務フローとダッシュボードでは当月、その他の画面では選択月を初期表示する。プレビューで対象月を変更できる。
